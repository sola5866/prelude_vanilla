# Documentation Style

このドキュメントは Prelude Vanilla のドキュメント作成ルールを定義する。

---

## 目的

ドキュメントの配置、責務、文体、用語を統一し、Build、Validation、Release の設計と運用を保守しやすくする。

ドキュメントは実装の代替ではなく、実装方針と運用ルールを共有するために管理する。

---

## 配置ルール

ドキュメントは `docs/` 配下へ配置する。

分野ごとにサブディレクトリを分ける。

```text
docs/
├─ build/
├─ validation/
└─ release/
```

新しい分野を追加する場合は、既存カテゴリに含められるかを先に確認する。

既存カテゴリに含めると責務が混在する場合のみ、新しいサブディレクトリを追加する。

---

## README の役割

README は目次として扱う。

README には詳細仕様を書かない。

README に記載する内容は次の範囲にとどめる。

* ディレクトリの目的
* 配置されているドキュメントの一覧
* 各ドキュメントの短い説明
* 読む順序

詳細な仕様、手順、設計判断は個別ドキュメントへ分離する。

---

## 1ファイル1責務

1つのドキュメントは1つの責務だけを扱う。

責務の例:

* Build 全体の流れ
* Workspace 変換
* 生成ファイル
* Validation の設計
* Release 手順
* Version ルール
* Branch 運用

複数の責務が混在する場合は、分割を検討する。

ただし、短い補足説明として関連ドキュメントへの参照を置くことは許可する。

---

## 命名規則

ファイル名は小文字の kebab-case とする。

例:

```text
build-system.md
build-transforms.md
generated-files.md
release-process.md
documentation-style.md
```

README は `README.md` とする。

ドキュメント名は内容の責務を表す名前にする。

---

## 見出しルール

見出しは以下の階層を基本とする。

```markdown
# Title

## Section

### Detail
```

`#` は文書タイトルにのみ使用する。

通常は `###` までにとどめる。

`####` 以降が必要になる場合は、文書の分割を検討する。

見出し名は短くし、同じ意味の見出しを複数文書で使い回す場合は表記をそろえる。

---

## 文体ルール

本文は常体で統一する。

推奨:

```text
〜する。
〜とする。
〜しない。
```

避ける表現:

```text
〜です。
〜ます。
〜してください。
```

手順や命令ではなく、ルールや設計方針として記述する。

---

## 箇条書きルール

箇条書きは `*` を基本とする。

同一ドキュメント内で `*` と `-` を混在させない。

番号付きリストは順序に意味がある場合のみ使用する。

箇条書きの文末は、短い名詞句の場合は句点を省略してよい。

説明文の場合は句点を付ける。

---

## コードブロックルール

コードブロックには可能な限り言語または形式を指定する。

例:

```markdown
```text
addons/
└─ Prelude_Vanilla_Main/
```
```

コマンド例には `bash` を使用する。

JSON 例には `json` を使用する。

ファイル構成やパイプラインには `text` を使用する。

---

## 用語ルール

以下の用語は表記を統一する。

```text
Addon
Workspace
Artifact
Build
Validation
Release
Release Draft
GitHub Actions
Git Tag
Version
```

日本語で説明する場合も、設計上の用語として扱う箇所では英語表記を優先する。

例:

```text
Addon Validation
Build Report
Release Workflow
```

同じ文書内で「成果物」と `Artifact` を併用する場合は、初出で対応関係を明示する。

---

## 参照ルール

関連する詳細ドキュメントがある場合は、重複して説明せず参照する。

例:

```text
Validation の詳細は `docs/validation/validation.md` を参照する。
```

外部リンクを記載する場合は、Prelude Vanilla 側で採用する仕様と外部仕様の境界を明確にする。

---

## 更新ルール

Build、Validation、Release の実装を変更する場合は、対応するドキュメントも確認する。

実装済みの内容とドキュメントの記述が矛盾しないように保守する。

将来予定の内容を書く場合は、現在実装済みの内容と明確に分ける。
